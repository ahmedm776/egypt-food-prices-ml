# Utility/calibration repair round (2026-11-05)

Two parts: (1) a calibration-method comparison under a frozen adoption rule - NEGATIVE,
isotonic retained; (2) a functional UI/API fix that exposes the raw ranking channel
separately from the calibrated probability - SHIPPED (presentation only; the model
bundle, metrics, thresholds, features and target are UNCHANGED).

## 1. Calibration comparison (calib_freeze.json frozen before fits; calib_results.json)
Origins 2016/2018/2020/2022 (selection origins only; shipped 2024-10 origin excluded),
frozen v4 config, arms raw / isotonic / positive-slope Platt. Fixed rule: adopt Platt
only if on EVERY origin auc_platt >= auc_raw - 0.005 AND mean(brier_platt) <=
mean(brier_isotonic) + 0.005.
Outcome: REJECTED. On the 2016-10 origin the Platt logistic slope came out NEGATIVE
(-0.9207), which REVERSES ranking (measured AUC 0.3055); the positive-slope guard caught
exactly the failure mode it was designed for. Other origins: Platt AUC == raw AUC
(ranking preserved as designed), Brier mixed (mean 0.2187 vs isotonic 0.2218 - within
margin, but the rank condition failed so no adoption). All origins development-exposed
robustness checks, not independent validation. No rule tweaking; comparison closed.

## 2. Functional fix shipped (src/app.py, templates/index.html)
The API and UI now expose two explicitly labeled channels:
- rank_signal_raw_score: raw model score - the ranking signal (which series is riskier);
- probability_estimate_calibrated: isotonic-calibrated score - a rough, unverified
  probability, with the documented drift limitation (2016-origin check: raw AUC 0.694 vs
  isotonic 0.644) and "ranking follows the raw score" guidance.
Existing response fields are unchanged (36/36 tests pass on a fresh unzip). Example of
why this matters, visible in the UI: Rice (Cairo) raw ranking signal 8% vs calibrated
estimate clipped to 0% by isotonic. The raw score is displayed UNITLESS (e.g. 0.08,
not 8%) so it cannot be misread as a probability; the calibrated estimate stays in %.
The big number is now captioned "calibrated probability estimate (rough, not verified)".
The app exposes the two channels but contains NO rank list (each request scores one
series); ranking guidance is for consumers comparing multiple series. No accuracy claim changed; no 95 claim;
utility/calibration repair only. Original model.joblib and metrics.json untouched.


## 3. Metric reconciliation vs rolling_origin_eval.json (read-only, 2026-11-05)
rolling_origin_eval.json (2026-11-04) documented the older v3 candidate config
(HistGB max_iter=600, lr=0.03, default l2=0, default max_leaf_nodes=31, seed 42);
its 2016-10 origin read raw AUC 0.720 / isotonic 0.563. This repair round's frozen
comparison used the SHIPPED v4 config (max_iter=200, lr=0.03, l2=1.0,
max_leaf_nodes=15, seed 42 - per src/train.py and models/metrics.json) on the SAME
data (sha256 08fac833...b70f), SAME origins/windows, SAME features. Re-running the
old v3-config harness on the current data reproduces rolling_origin_eval.json
exactly (2016: raw 0.7203 / iso 0.5629 / brier 0.2015; 2018: 0.6295 / 0.6303 /
0.1592), so the numeric difference vs this round (2016: raw 0.6945 / iso 0.6439)
is fully explained by the model-config difference, not by data, windows, features,
or seed. Historical metrics are NOT overwritten: rolling_origin_eval.json remains
the v3-config record; calib_results.json is the v4 (shipped pipeline) record. Both
are development-exposed robustness checks, not independent validation.

## 4. Stale-result fix (2026-11-05, same round)
The result panel could keep showing a score after the user changed the Price series or
Commodity selector (selection/result mismatch). Fixed: any selector change now clears
the result panel and error (clearResult wired to both change events), requiring a fresh
score for the current selection. Regression tests in tests/test_ui_template.py;
verified in the browser: Rice scored, selector switched to Arugula, stale result cleared.
